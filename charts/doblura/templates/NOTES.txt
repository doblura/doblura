{{- if and (gt (int .Values.replicaCount) 1) (not .Values.leaderElection.enabled) }}

  IMPORTANT WARNING: replicaCount = {{ .Values.replicaCount }} without leader election.

  Two managers reconciling the same OdooRehearsal would create the migration Job
  TWICE against the same database. An Odoo migration is not idempotent: that
  corrupts the rehearsal's database.

  Fix it with:
      --set leaderElection.enabled=true
{{- end }}

{{- if eq (int .Values.replicaCount) 0 }}

  WARNING: replicaCount = 0. The operator is not running and every OdooRehearsal
  will sit in Pending forever. The quota webhook is not installed either, so
  OdooTenant.spec.maxEphemeralEnvironments is not being enforced.
{{- end }}

{{- if and (not .Values.webhook.enabled) (gt (int .Values.replicaCount) 0) }}

  WARNING: webhook.enabled is false. OdooTenant.spec.maxEphemeralEnvironments is
  then a number nobody reads: one person can open as many environments as they
  have patience for, and the cluster runs out first.
{{- end }}

{{- if and .Values.webhook.enabled (gt (int .Values.replicaCount) 0) }}

The quota webhook is installed with failurePolicy Fail, which means that until the
manager is up and has published its CA, creating an OdooEnvironment is refused.
That is on purpose — a quota that disappears when the operator does is not one —
and it clears itself within a few seconds. Check it with:

    kubectl get validatingwebhookconfiguration {{ include "doblura.fullname" . }}-quota \
      -o jsonpath='{.webhooks[0].clientConfig.caBundle}' | head -c 20

  An empty caBundle means the manager has not got there yet.
{{- end }}

{{- if not .Values.rbac.create }}

  WARNING: rbac.create is false. Make sure the ServiceAccount
  {{ include "doblura.serviceAccountName" . }} already has permissions on
  odoorehearsals, jobs, configmaps and secrets.
{{- end }}

Before your first rehearsal you need two things Doblura does NOT create:

  1. An anonymized dump of production, on a PVC, in S3, or anywhere else.
     Producing it is your problem and your regulator's: Doblura consumes it.

  2. A Postgres server whose user has CREATEDB. Every rehearsal creates its own
     scratch database and drops it when it finishes.

Check that it started:

    kubectl -n {{ .Release.Namespace }} rollout status deploy/{{ include "doblura.fullname" . }}

And launch the first one:

    kubectl apply -f https://raw.githubusercontent.com/doblura/doblura/v{{ .Chart.AppVersion }}/config/samples/odoorehearsal-volume.yaml
    kubectl get rehearsal -w

Remember: neutralize defaults to true, and it should stay that way. A production
dump restored without neutralization sends real invoices to real customers.

{{ if .Values.personas.create }}
The five personas are installed as ClusterRoles. Bind viewer to the group your
identity provider gives everyone who should see this platform — it is the floor
the others add to, and it is what answers "is it up" in the console:

    kubectl create clusterrolebinding doblura-viewer-all \
      --clusterrole={{ include "doblura.fullname" . }}-viewer --group=<your-everyone-group>

Do NOT use system:authenticated. Every ServiceAccount in the cluster belongs to
it, so that binding hands every customer record to every pod with a mounted
token, in every namespace.

Then bind support, qa, consultancy and platform to your own groups.
{{- end }}
{{- if .Values.console.enabled }}

The console is serving on {{ include "doblura.fullname" . }}-console. It holds no
permissions of its own: every request is impersonated as the person who signed
in, so Kubernetes RBAC is the only authorization in the system.
{{- if not (or (.Values.console.oidc).issuer (.Values.console.localAccounts).secretName) }}

is set, and it refuses to serve traffic it cannot attribute to anybody.
{{- end }}
{{- end }}
